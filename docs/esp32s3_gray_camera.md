# ESP32-S3 摄像头联调（彩色 / 灰度）

## 当前阶段：摄像头、双振动马达与 MAX9814 麦克风（2026-11-19）

当前固件已启用双马达：左侧 `GPIO40`、右侧 `GPIO41`，前方同时驱动两路，
单次振动 300 ms。`GPIO1`（ADC1）连接 MAX9814 的 `OUT`；2026-11-19 编译烧录并
测到安静时约 184–211、说话时约 780–1199 的 ADC 峰峰值，确认模拟信号随声音变化。
固件目前只做低频电平诊断，音频采集上传和语音识别尚未接通。

本机通过 COM3 读取到 ESP32-S3，Flash 为 8 MB，内置 PSRAM 为 8 MB。
新固件会打印 PSRAM 容量、传感器 PID、Wi-Fi IP / RSSI、发送与 ACK 计数、
抓帧失败次数，帮助区分相机、网络和后端问题。

本机已读到摄像头为 **GC0308，PID `0x009b`**。先前灰度是采集格式配置，
不代表传感器只能输出灰度；当前默认使用 `CAMERA_COLOR_MODE=1`，采集
320×240 RGB565 彩色图，再由 ESP32 软件压缩成 JPEG 上传。摄像头引脚和
8 MHz XCLK 保持原配置。

## 当前硬件与必须处理的引脚冲突

用户报告板卡为安信可 ESP32-S3-CAM、芯片 ESP32-S3R8，已经能采集
320×240 灰度图。新示例保留用户已跑通的摄像头映射和 8 MHz XCLK，
不据此断言所有同名板卡或传感器都使用相同配置，也不要求更换成 JPEG 采集。

**2026-11-18 确认的冲突：**

| GPIO | 用户提供的摄像头用途 | 电机配置情况 |
| --- | --- | --- |
| 4 / 5 | SCCB SDA / SCL | 原贴代码将它们定义成电机控制脚，冲突 |
| 10 / 11 | D3 / D0 图像数据线 | 用户确认电机实际接在这里，同样冲突 |
| 1 | ADC1 输入，摄像头配置未使用 | MAX9814 模拟 `OUT` |
| 2 | 摄像头配置未使用 | 已空出 |
| 40 / 41 | Freenove ESP32-S3-WROOM 板上排针引出 | 当前固件左 / 右马达驱动 `IN` |

先断开电机驱动连接到 GPIO10/11 的两条控制线。软件关闭电机输出不能消除
外部电路对摄像头数据线的电气影响。重新选择电机控制脚时，应对照确切板卡版本
原理图，排除摄像头、Flash/PSRAM、USB、启动配置及其他实际使用的外设。
GPIO40/41 是根据用户实物板排针标号选择的；更换板卡版本时需重新核对。
马达模块带 MOS 驱动，不由 GPIO 直接供电。两个模块 VCC 并联接 ESP32
单个 5V 脚、GND 与 ESP32 共地；模块规格为额定 5V、最大启动电流 90mA/个，
两路同时启动约 180mA，若相机或 Wi-Fi 重启，应改用独立 5V 电源。

在原后端终端按 `Ctrl+C`，然后从项目根目录启动：

```powershell

conda activate yolo-blind
python -m uvicorn backend.main:app --host 0.0.0.0 --port 8765 --ws websockets --ws-ping-interval 20 --ws-ping-timeout 20 --ws-max-size 1048576
```

本次检查发现另有 Python 服务运行 `app.main:app` 并监听 8000；它与本项目
`backend.main:app` 的 8765 服务不是同一个入口。没有修改或停止该服务。

健康检查：`http://电脑IPv4:8765/api/health`。该接口可确认设备 ID 和模型状态，

## 2. 使用新的独立固件示例

打开：

```text
firmware/esp32s3_gray_camera/esp32s3_gray_camera.ino
```

同目录的 `config.h` 是这个示例的配置；不要改错成上一层旧固件的 `config.h`。
可在同目录创建 `config.local.h` 填写自己的 Wi-Fi 和电脑 IP，它优先于共享默认值，
并已由项目根目录 `.gitignore` 排除。不要分享本地凭据文件或包含凭据的固件备份。

`config.local.h` 示例（仅本机保存）：

```cpp
#pragma once
#define WIFI_SSID "你的WiFi名称"
#define WIFI_PASSWORD "你的WiFi密码"
#define BACKEND_HOST "电脑当前局域网IPv4"
#define BACKEND_PORT 8765
```

共享 `config.h` 中的连接路径与马达禁用配置为：

```cpp
#define WIFI_SSID "你的WiFi名称"
#define WIFI_PASSWORD "你的WiFi密码"
#define BACKEND_HOST "电脑当前局域网IPv4"
#define BACKEND_PORT 8765
#define CAMERA_JPEG_TRANSPORT 1
#define CAMERA_COLOR_MODE 1
#define CAMERA_JPEG_QUALITY 65
// config.h 根据传输开关自动选择路径：
#define CAMERA_WS_PATH "/ws/camera?device_id=esp32s3_cam_001&protocol=2&format=jpeg"

#define ENABLE_MOTORS 0
#define MOTOR_LEFT_PIN -1
#define MOTOR_RIGHT_PIN -1
```

先保持 `ENABLE_MOTORS=0`，完成图像上传和指令接收验证。确认替代引脚并完成
接线后，再填写两个 GPIO、设置 `ENABLE_MOTORS=1` 并重新编译烧录。
编译期会拒绝摄像头冲突脚、相同左右脚及部分已知不适合本方案的资源脚，
但通过编译不代表完成板级接线审核。

依赖使用本机已安装的 ESP32 Arduino Core、WebSockets，无需 ArduinoJson。
默认采集 320×240 RGB565 彩色图，由 Core 自带的 `frame2jpg` 在 ESP32 上软件压缩，
不要求传感器支持原生 JPEG。设置 `CAMERA_COLOR_MODE=0` 并重新编译烧录，
可回到灰度采集；网页和后端均不需要因此修改。
Arduino IDE 中保留原来成功采集时使用的板卡、Flash 和 PSRAM 配置。
代码要求 PSRAM 可用；未发现 PSRAM 或相机初始化失败时不会继续抓帧。

本机可使用 Arduino IDE 自带 CLI 做编译检查（不连接串口、不烧录）：

```powershell
$arduinoCli = "$env:LOCALAPPDATA\Programs\arduino-ide\resources\app\lib\backend\resources\arduino-cli.exe"
& $arduinoCli compile --fqbn esp32:esp32:esp32s3:FlashSize=8M,PartitionScheme=default_8MB,PSRAM=opi,UploadSpeed=115200 firmware\esp32s3_gray_camera
```

这里的 FQBN 已用于本机 COM3 实物的编译和烧录：8 MB Flash、默认 8 MB 分区、
OPI PSRAM。其他板卡版本仍需重新核对参数和实际端口。

## 3. 通信格式与稳定性改动

完整链路：

```text
ESP32 RGB565 / 灰度采集 → 软件 JPEG → /ws/camera?format=jpeg → 校验 → 最新帧缓存 / YOLO 队列
                                                              ↓          ↓
                                                       网页 / 平板预览  方位 → L/R/B
```

- 优化版默认 `CAMERA_JPEG_TRANSPORT=1`，使用 `format=jpeg`，每个 WS 二进制
  消息是一张完整 JPEG。质量为 65（转换器的 1～100 标度），分辨率为 320×240。
  `CAMERA_COLOR_MODE=1` 采集 RGB565（原始帧 153,600 字节），设为 0 则采集灰度
  （原始帧 76,800 字节）。这些原始帧在 ESP32 内压缩，网络上传输 JPEG。
  后端限制不超过 256,000 字节，先检查 JPEG 尺寸再解码验证，并直接保留原压缩数据，
  不做第二次有损编码。
- 旧版原始帧仍兼容：不带 `format` 或 `format=gray` 时，每帧必须是
  320×240×1 = **76,800 字节**。没有 `QH` 头，后端先转换成 JPEG。
  原始帧回退时将 `CAMERA_COLOR_MODE=0`、`CAMERA_JPEG_TRANSPORT=0` 并重新编译烧录，
  路径与间隔会自动匹配原协议；编译期会拒绝原始彩色帧误发到灰度协议的配置。
- 两条图像路径复用现有检测器和平板缓存。图像队列容量为 1，
  忙时丢弃待处理的旧帧；ACK 不承诺每张图都执行推理。
- JPEG 模式在收帧 ACK 后至少等待 **40 ms** 再采集 / 上传；原始帧回退模式仍等待
  1,200 ms。只在 WS 已连接且相机就绪时发送，始终只允许一帧等待 ACK。
  40 ms 是调度间隔，不等于能达到 25 FPS；还需要叠加采集、编码和网络耗时。
- 网页远程预览取图周期从 700 ms 缩短为 **150 ms**，最多一个取图请求在途。
  预览不等待 YOLO 完成；检测忙时继续使用最新帧策略，识别帧率与预览帧率分别评估。
- `protocol=2` 时后端收帧并入队后返回文本 `ACK`。未收到 ACK 不继续传图；
  **完整 TCP 发送成功后**才开始计时，等待超过 5 秒会重连。发送前开始计时会把
  慢发送错误算成 ACK 超时，本机曾实测单帧发送耗时 11～13 秒。
  串口分别显示压缩后字节数、编码耗时、TCP 写入耗时和发送后的 ACK 等待时间。
  ACK 只表示后端接收，不是识别成功或电机执行确认。
- 固件启用 WS Ping/Pong（15 秒间隔、15 秒等待、连续 2 次超时断线），
  并设置 3 秒重连间隔。Wi-Fi 重连与 WS 连接状态分开维护。
- 接收指令时启动震动计时，主循环负责停止，回调中没有 `delay(300)`。
  震动期间不抓帧上传；网络断开时关闭输出。计时仍受主循环调度影响，不是硬实时。
- 接收和推理解耦；灰度编码和 YOLO 推理使用工作线程，避免在 WS 接收函数中
  同步执行模型推理。并发写入有锁，单次发送有超时。
- 同 ID 灰度设备重连会替换旧连接；旧连接退出不会删除新连接或它的预览。
  连续 30 秒没有应用层图像消息时后端关闭连接。
- 错误帧返回文本 `ERR:BAD_FRAME:...`，不会作为图像送入 YOLO；
  不支持的文本上传返回 `ERR:EXPECTED_BINARY_QVGA`。

| 检测方位 / 操作 | protocol=2 | 默认兼容模式（不带 protocol 参数） |
| --- | --- | --- |
| 左侧 | 二进制 `L` | 二进制 `L` |
| 右侧 | 二进制 `R` | 二进制 `R` |

### 旧版 LU6288 UART 语音（历史记录，当前已停用）

> 以下记录用于追溯旧硬件联调。当前固件不再向 GPIO21 发送 LU6288 文本，LU6288 模块已更换；现行帽端播报使用下方 Edge TTS 音频下行与 MAX98357A I2S。

- 协议 2 帽端会播报连续两帧确认的新物品及方位；目标持续可见时不会逐帧重复，离开画面约 3 秒后再次出现会重新播报。
  紧急障碍物告警仍会附加“请注意”，并优先于普通物品播报。语音开关关闭时，两类硬件播报都会停止。
- 后端发送二进制下行消息：ASCII `T` 前缀 + LU6288 文本命令。ESP32 剥掉 `T` 后经 9600 baud UART
  发送 `<G>` 与 GBK 中文文本；COCO 类别映射为中文。这个格式依据用户在 SSCOM / CH340 上成功播报的
  `<G>前方有人` 实测。
- 固件校验前缀和消息长度后，经 `Serial1` TX GPIO21 原样送入 LU6288 `RX`；
  模块 `TX`、`BUSY` 暂不连接。代码默认 UART 仅发送，设备播报状态没有回传确认。
- LU6288 `5V` 接稳压 5V，`GND` 与 ESP32 共地，`SP+ / SP-` 接随附扬声器；
  ESP32 GPIO 输出为 3.3V，接入模块 RX 前需确认模块接受 3.3V UART 高电平。
  GPIO21 必须在板上引出并保持空闲，不能仅凭编译通过视为板级接线确认。
- Python 测试验证普通物品、紧急告警文本和 GBK 编码；用户已确认 ESP32 经 GPIO21 驱动 LU6288 喇叭出声。
  电脑网页语音仍独立运行。模块 TX/BUSY 未接，后端没有模块播报完成回执。
- 套件 CH340 隔离验证已确认有声：断电后先拔掉 ESP32 GPIO21 到 LU6288 RX 的线，
  将 CH340 `TXD → RX`、`GND → GND`、`5V → 5V`，喇叭仍接 `SP+ / SP-`；
  不连接 CH340 RXD，也不要同时让 ESP32 TX 与 CH340 TX 驱动模块 RX。连接 CH340 USB 后，
  在项目目录运行 `python tools\\test_lu6288.py --port COMx`（将 COMx 换成 CH340 的端口）。
  该测试确认模块、供电和文本格式可用。集成时 LU6288 RX 曾误接 ESP32 板上 `TX`；
  固件实际使用 GPIO21。改接到 `IO21` 后用户确认播报成功，CH340 已可移除。
- 2026-11-19 联调的一段 12 秒检测窗口中，后端返回 `person`、`tie`、`vase` 等类别，
  ESP32 串口记录到 8 条对应语音命令。若画面里没有这些目标而仍播报，应检查 YOLO
  误识别和摄像头当前视野；播报由真实模型输出触发，不是摄像头离线提示。
- 当前 `<G>` 文本命令没有调整 LU6288 的音量或音色，模块仍使用默认值。可调范围和控制
  命令尚未从该模块的资料中核实；拿到 LU6288 随附协议或卖家控制命令后再实现设置。

### Edge TTS 音频下行与 MAX98357A I2S

当前电脑侧以高频语句 WAV 缓存为优先；文本未命中时，由 Edge TTS 生成音频，经 FFmpeg 转为 16 kHz、16-bit、单声道 PCM，并写入本地语音库。Edge TTS 合成失败会报告失败状态，不会假报已播放。

- `/ws/tts?device_id=esp32s3_cam_001` 是独立连接；摄像头继续使用 `/ws/camera`，麦克风上传继续使用 `/ws/audio`。
- 固件 `tts_player.h` 在独立 FreeRTOS 网络任务中收取协议 v1 的 START/CHUNK/END/CANCEL 帧；有限长度队列把音频块交给专门 I2S 写任务。摄像头采集和马达输出不会同步等待音频播放。
- 播放格式为 16 kHz PCM S16LE 单声道，面向 MAX98357A；固件按 START 中的长度和 CHUNK 序号校验，再发送 READY、PLAYBACK_STARTED、PLAYBACK_DONE、PLAYBACK_ERROR 或 PLAYBACK_CANCELLED 回执。
- `config.local.h` 可配置 `TTS_I2S_BCLK_PIN`、`TTS_I2S_LRCLK_PIN`、`TTS_I2S_DIN_PIN`。三个宏目前保留为 `-1`；I2S 未配置时设备拒绝播放并回报错误码，不会声称播放成功。
- 电脑端实时合成依赖 `edge-tts` 与 FFmpeg；安装 `python -m pip install -r backend/requirements-tts.txt`，FFmpeg 必须能从后端进程的 PATH 或 `TTS_FFMPEG` 指定路径找到。
- 软件模拟可运行 `python tools/tts_hat_simulator.py --device-id esp32s3_cam_001`。可选 `--play` 会通过电脑自己的扬声器试听，不能代表帽端 MAX98357A 真机播放。

目前尚未补录三个 MAX98357A GPIO，也尚未为此链路重新编译/烧录和在帽端扬声器上试听。原来摄像头与马达单独协议保持独立，不应把 TTS PCM 混入其中。

新示例的每次震动固定 300 ms。该单字节协议不携带可变 `duration_ms` 或执行回执。
原来的 `/ws/device` 与 `QH` 头协议保持独立，不应把两种帧格式混用。
`/ws/camera` 是本地联调兼容接口，当前没有设备鉴权，不应暴露到公网。

## 4. 按顺序验收

1. **采集与上传：** 先断开冲突电机控制线、保持电机禁用，烧录新示例。

   JPEG 模式下的 `Frame format=jpeg, bytes=...`、`send=ok`、`Frame ACK`。

2. **画面：** 网页更新后先重启后端（监听 `0.0.0.0:8765`），浏览器按 `Ctrl+F5`，
   登录后在“实时环境监测”顶部统一的“摄像头”下拉框选择“ESP32 帽端摄像头”，
   点击“查看帽端画面”。该项对应 `esp32s3_cam_001`，没有新鲜画面时标注“等待画面”。
   已有平板 App 则在“摄像头来源”中选择“帽端摄像头 esp32s3_cam_001”。
